# SUTRA 110-second browser proof sequence — planning storyboard

**Planning duration: 110 seconds. Hard submission ceiling: <120 seconds.**  
This is a storyboard, not a recorded/public demo. Entrant narration and final browser timing remain human gates.

The story must prove one coherent learner outcome first, then show why the agentic-web mechanism matters. No slide may claim factual truth, public adoption, production capacity or live-provider economics that have not been observed.

## Required visible moments

The edit must visibly contain, not merely narrate:
1. exact source/cue identity;
2. native seek feedback;
3. separate video/written source cards;
4. unresolved conflict;
5. pre-save receipt preview;
6. consent dialog before contact;
7. denial with zero-contact outcome;
8. caller-local peer execution or a clearly labeled current executable demonstration;
9. one bounded failure/cancellation state;
10. reusable Open Kit surface/result.

## Narration budget

110 seconds leaves little room for exposition. Target approximately **235–260 spoken English words** at ~128–142 wpm, allowing pauses for on-screen proof. The narrator should explain mechanism, not read UI labels.

Suggested narrative beats:
- 0–25s: problem and evidence retrieval (~55 words)
- 25–56s: provenance and disagreement (~65 words)
- 56–77s: explicit review/action (~40 words)
- 77–103s: agentic composition, consent and limits (~65 words)
- 103–110s: reusable contribution (~20 words)

This word budget is prospective. The final entrant must perform the script naturally; P005-08 remains open until the actual human narrator demonstrates the storyline can be explained in their real voice.

## Edit rules

- Browser operation is primary footage; avoid hiding behavior under slides.
- One brief title card is acceptable only if it does not displace executable evidence.
- Use cuts to remove loading/dead time, not to fabricate an operation that never completed.
- Do not speed video so much that consent/source text becomes unreadable.
- Do not show a model answer as the proof of source truth; source cards/receipts are the proof of consistency.
- If funded inference is not ready at recording time, do **not** fake it with the synthetic provider. Use the zero-model core path and clearly label any developer-only model demonstration.
- If public peer interoperability is not ready, do not imply the loopback/same-owner peer is independent infrastructure.
- Never narrate “verified fact,” “production-ready,” “used by developers,” or “works on all phones” without the corresponding current evidence.

## Failure branch if something is not ready

Priority order for the final 110 seconds:
1. exact evidence + native seek;
2. comparison/uncertainty;
3. explicit review/save;
4. consent + denial;
5. caller-local peer composition;
6. reusable Open Kit;
7. optional model inference.

Optional inference is the **first cut**, not source evidence or consent.

## Counterexample / judge challenge

A judge can ask: “Why not Ctrl+F the transcript?” The demo should make the answer observable rather than rhetorical:
- literal lookup itself is intentionally simple/zero-model;
- added value is source/media identity, actual seek, separate written provenance, disagreement preservation, explicit review receipt and portable consented composition.
The future paired user test must still determine whether this is actually faster or more useful than manual search.

## Recording gates

Do not record the final competition demo as submission-ready until:
- rights-cleared real lesson/guide and factual reviewer exist;
- exact public candidate revision is known;
- any shown external peer is truthfully labeled by ownership/independence;
- free judge path is usable;
- physical/human accessibility claims in narration are limited to actual evidence;
- final narration comes from the genuine entrant.

Storyboard completion does not satisfy these gates.
