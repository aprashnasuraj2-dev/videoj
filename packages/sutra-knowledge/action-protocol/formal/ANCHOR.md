# Multi-key anchored recovery candidate (V2-010)

The original Recovery.tla and its safe/unsafe configurations remain unchanged. AnchoredRecovery.tla is a separate finite abstraction: two callers, two authorized logical keys, one unauthorized key, at most two per-caller contacts and three aggregate contacts, bounded pending deliveries, one trusted authoritative CAS history. A committed history is also recorded in a conceptual independent pin set even if an acknowledgement is lost. The model does not claim all clients actually receive every head.

Safety: exact parent comparison, ordered unique authorized keys, receipt soundness, nondecreasing published prefixes, no forks, bounded contacts. Four mutants deliberately remove authorization, the budget, rollback resistance, or stale-parent rejection. Each must violate its named invariant; tool/download/parser errors are not evidence.

Mapping: Dispatch and Status reserve contact before transport; this reservation is an abstract requirement, not yet a durable client implementation. Drop models lost delivery. Deliver maps to Anchor.Advance's parent comparison and underlying DurableReceiver.Commit; ack=false abstracts lost reply. Crash preserves authoritative history and counters; existing process tests cover the receiver, not a physical power failure or client journal. Rollback is forbidden only for the independently trusted anchor itself. The clone counterexample in Go deliberately violates this trust assumption. Go verifier checks a supplied independent pin; it is not a proof of freshness.

No unconditional liveness: an authorized commit without acknowledgement can outlast all available contacts. The independent Python exploration requires such a reachable state. Conditional recovery additionally requires eventual service availability, a correct authority, a delivery/status opportunity, and a remaining or explicitly renewed trusted contact budget. Fairness and a formal Go refinement proof are not claimed. No general consensus, Byzantine quorum, arbitrary upstream effects, or approval expiry/revocation. All requirement promotions await exact evidence.
